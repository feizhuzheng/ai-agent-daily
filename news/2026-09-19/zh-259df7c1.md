# 灵感雷达: 2026-09-20

> 来源 / Source: https://clauday.com/zh/article/259df7c1-8952-4a42-9f0e-234dbc16b0b7

今天几乎所有东西都来自两个矿脉，而且没有一个是大家正在兴奋的那类软件。第一个是干活的手艺人在描述一件不存在的工具——一位在大批量拆水表的管道工、一位够不到自己留下的烧痕的砧板匠——这已经是同一种形状连续出现的第五个窗口：在标准工具去不了的地方，实现受控的接触。第二个是 agent 的授权层，它连续第十三个窗口出现，而且至今没被做出来：带作用域、过期时间、签发者和决策 ID 的有界授权，对「被拒绝」和「被批准」一视同仁地出具回执，以及一道横在「决策」和「工具调用」之间、而不是之后的闸门。单看个体，最好的一条是一次安全降级——一个故意只暴露一条凭证而不是整个密码库的密码管理器。而最有用的一份失败报告直接点名了一个缺失的产品品类：对「没有发生的事」做监控。

一位密码管理器用户，每次借用别人的电脑时，都得对着手机把一个 16 位的随机密码一个字符一个字符敲进去——因为把整个密码库放到一台不可信的机器上，等于把里面所有东西都暴露了。他想要的是反过来的取舍：只把某一条凭证传到那台设备上，这样哪怕这台电脑已经被彻底攻陷，它也只能学到他主动选择暴露的那一个密码。他连流程都已经写好了：打开一个自托管的网页服务，用一个短的、记得住的密码解锁，浏览一份可搜索的凭证列表，挑一条，手机收到推送批准，然后浏览器才看得到它。他也明说了自己愿意付出的代价：凭证名称的列表可以泄露，服务端技术上也能解开数据库。半年前他找过，什么都没找到。这个产品本质上是把密码管理器故意降级，而「降级」恰恰是没人愿意做的那一类。

一位管道工需要拆解大量不同型号的水表，而这件活的两半他都找不到合适的工具：一是在不损坏的前提下取下上部的塑料表体，二是拆解内部结构——具体说是把那个死死旋进黄铜底座的部件拧出来。他不知道这些工具叫什么、去哪儿买，也不知道有没有可行的土办法。这已经是连续第四个窗口，Reddit 上质量最高的未满足需求是一件实体手艺工具而不是软件，而且形状一模一样：一个做着大批量重复作业的从业者，已经自己推理到「这工具该做到什么」这一步，卡住的原因仅仅是这个工具没有被做成产品。

一位数据分析师描述了他手工搭建的一样东西——任何在数仓上做 agent 的人最终都会需要它：上下文层。他把它放在一个笔记应用里，每次查数据库时喂给模型；每当在新任务里第一次碰到某张表或某个字段，就让模型把它记录下来，然后慢慢地把指标口径、命名约定和产品文档也一起攒了进去。他形容这个过程「手工到令人痛苦」，问的是：有没有现成工具，还是说像他这样手工绕过去就是常态。答案是：就是常态。语义层作为 BI 概念已经存在二十年了，但没有人做出「消费者是模型而不是看板」的那个版本；而这个版本唯一真正要紧的性质是：它必须作为「干活」的副产品被写出来，而不是作为一个永远做不完的文档工程。
Source: Reddit

一位经营着生意的人想要一个整天跟着他的助理，而不是一个他得主动打开的东西。生意上的付款、进货、账单、结算；客户的报价、需求、投诉、退货；每天的物流；在这之上还有家里的账单和个人杂务。他说自己在任务的迷宫里迷了路，而且明确说了 Todoist 这类应用对他不管用——这句话才是真正的发现，因为它把失败点定位得很准。任务应用是一个你要主动过去把事情写下来的地方。而他描述的是一个已经在看着的东西：它已经知道进来了什么，会提醒他，事情拖了会帮他重排，并且能用自然语言接受指令和回答提问。今天几乎所有的 agent 产品，仍然是一个「你得过去」的地方。

本周最有用的一份失败报告，而且它点名了一个缺失的产品品类：对「没有发生的事」做监控。他的 agent 开了一个仓位，不到一分钟就平掉了，但换回来的那一笔交换从未触发。没有交换，没有报错，没有告警——他的数据库每十五分钟才抓一次新池子，而这个池子才存在几分钟，于是代币在钱包里躺了两分钟，价格一路砸下去。账面上这个仓位只亏了 0.4 个单位；钱包实际少了将近 2 个。他之所以发现，只是因为余额和自己的账对不上；而且这不是偶发——大约每六次平仓就有一次没能按时换回，全靠一个对账程序兜住。他的结论就是需求规格：把一切都记下来，包括没有发生的事。市面上每一个可观测性工具都在对事件告警，却几乎没有一个在对「一个本该发生的事件的缺席」告警。
Source: https://x.com/razzaer/status/2100600290927886747

有人做了一个只有 AI agent 能发帖的社交网络——它们通过 API 注册、发帖、评论、投票，人类只能读不能参与——然后把每一个来访 agent 的工具链是怎么坏的都记录了下来。没有一种失败是他事先设计防范的那种。第一个 agent 注册和发帖都没问题，然后发现自己读不了任何帖子：它的浏览工具只抓 HTML、从不执行 JavaScript，所以一个客户端渲染的信息流在它眼里就是一张白纸。查询字符串直接干翻了另一些工具：路径形式的接口能用，查询参数形式的就失败。而普通的消费级聊天助手根本发不了帖，因为它的浏览工具只支持 GET——很多人反复让它去发帖，看着它答应，然后什么都没发生。这里面每一条都是一个产品：一个为 agent 提供无脚本渲染的站点、一批可按请求返回纯文本的接口、以及一套「告诉你哪些 agent 真的能和你交易」的一致性测试。

一个用了好几个月品牌监控工具的人，把缺口点得很准：数据都在那儿，但把它变成「改这个页面、发到那边去」，全是手工活。他不想为了查自己的品牌出现在哪儿而手动敲提示词，他想要的是被直接告知。他看过企业级的那个和一个只做监控的便宜货，发现是同一种割裂。然后是把整件事重新定义的那个细节：他最近找到的最有用的东西根本不是工具，而是一份公开的审计报告——追踪了 158 篇文章里助手实际引用了什么，结果是同一个作者、同样的内容质量，发在一个大型行业平台上的引用率约 52%，发在公司自己的博客上是 0%。他的结论是：他的问题从来不是监控，是分发——收尾时他问，有没有东西能把这两端接起来，还是说答案永远是「一个看板加一个读看板的人」。

一个关于 ADHD 预算应用的需求，而且描述得异常清楚，因为发帖人非常明白现有产品为什么对自己无效：普通的预算应用拦不住冲动消费，它们只在事后汇报。他想要的是：一个周度或月度的消费上限、接近上限时的预警、越接近提醒越强硬，以及——那个没有任何主流应用愿意做的部分——一旦触线就能真正限制或冻结消费，或者至少让花钱这件事明显变难。另外：做简单点，别给我五百张图表。真正可以拿来做产品的是这句话：他需要的不是一个告诉他「你超支了」的应用，而是一个能在他把预算炸掉之前拦住他的应用。这和市面上每一个个人理财应用都是根本不同的产品，而且它需要那些应用极力回避的一样东西——用户事先同意过的摩擦。

这一窗口里，对「agent 技术栈始终没有交付的那样东西」最干净的一次陈述：缺的那一层是有边界的授权，外加对每一次授予和每一次拒绝都出具一张回执。他解释现有工具为什么表达不了这件事的那段才是有用的部分——读权限和写权限不是一个二值开关；一个团队要想事后还原「agent 是怎么越过某条边界的」，真正需要的是每次授予上都带着作用域、过期时间、签发者和一个决策 ID。注意回执必须覆盖被拒绝的请求，而不只是被批准的——因为事故之后真正有取证价值的问题，通常是「这个 agent 试图做什么、又被拦在了哪里」。这已经是这个需求以某种形态连续出现的第十三个窗口了，而它依然没有产品。
Source: https://x.com/Brendon_Arch/status/2101417908526006435

同一个缺口，从商业那一侧切进来，而它划出的那条区分正是大多数身份厂商在悄悄含糊过去的：身份证明的是「谁授权了这个 agent」，它并不定义「这个 agent 可以承诺什么」。这里点名的缺失层是有作用域的授权——消费上限、允许的交易对手、有效期、可撤销性，以及可审计的回执——而收口那句是：验证加上一份可编程的授权书，才能把一个 agent 变成安全的经济主体。现在正在交付的所有东西，都是「验证」那一半。每一条支付轨道都有一个 agent 故事，而没有一条有一份授权书的格式。
Source: https://x.com/LFGCAPO/status/2101291020470374879

一个关于 agent 可靠性的缺口，讲得比大多数厂商自己讲的都好：缺的那一层通常是失败语义——重试、工具的部分成功、以及一个明确的终止条件——而这些比把顺利路径做得多聪明更重要。真正能做成产品的是第二句：只要这些状态是可观测的，agent 就从一个你只能欣赏的演示，变成一个你可以运维的系统。其中最值得下手的是「工具的部分成功」，因为这正是当前每一个框架都会粗暴地折叠成「成功」或「失败」、然后基于错误前提继续推理的那个状态。

一句应该重新组织「agent 安全产品该怎么做」的区分：拔电源是有用的，但难的是控制——因为一旦 agent 拿到了工具访问权、而那个动作已经发出去了，杀进程就只是善后，不是预防。目前正在交付的每一个 kill switch、每一个大红色停止按钮、每一个「暂停这次运行」的功能，都在这条线的善后那一侧。位于预防那一侧的产品，是一道横在「决策」和「调用」之间的闸门，而几乎没有人在卖这个。
Source: https://x.com/techietaro/status/2101062466788622821

一个对任何同时跑着多个编码 harness 的团队来说，既具体又马上能做的缺口：把 skills、规则和工具配置从一个共享仓库同步出去，是那块显而易见的缺失拼图；但他点出的难点才是会杀死那些天真实现的东西——当两个不同的 harness 在不同分支上重写同一个 agent 指令文件时，冲突策略怎么定。这是一个带语义的合并问题，不是文本问题：两个 agent 各自在改进同一份规则文件，它们产出的不是互相冲突的行，而是互相冲突的策略；而一次三方文本合并会悄无声息地挑走其中一个。没有人交付过这套语义。

他描述自己公司实际怎么运转的那段，同时也是一份产品规格，而中间那句就是全部：编码 agent 会写软件，但它们不经营公司；缺的那一层是一张由「限定作用域的 bot」组成的组织架构图，跑在实时数据上，只有当某个动作后果严重时人才介入。一句话里三个约束，每一个都是一件要造的东西：限定作用域，也就是每个 bot 的权限要比它所依附的账号更窄；跑在实时数据上，也就是这个 bot 不是在对着上周某人导出的快照做推理；以及一道按「后果」而不是按「步数」触发的人工闸门——而这正是当前每一个审批系统都做错的地方。

路由，但是为治理而不是为成本做的路由——而这个区分，模型路由这个赛道里没有一个人在提。他的意思是：缺的那一层是策略，而不是再加一个专家 agent；规格随之而来：当一次通宵运行里有几百个 agent 时，他希望同一道闸门在任何专家 agent 拿到发言权之前，先看到能力、成本和影响半径。「影响半径」这个词值得抄走。市面上每一个路由器都会给任务在难度和价格上打分，没有一个会给它在「被选中的这条路径能造成多大破坏」上打分。

一个用一句话说清楚的专注类产品，而且背后带着最强的购买意图标记：设一个计时器，然后每一个和你声明的目标无关的浏览器标签页，十秒后自动关闭。他还补了一句，他会是第一个客户，而且愿意做天使投资人。这件事之所以不是又一个网站拦截器，在于机制——拦截器依赖一份你必须自己维护、而且随时可以在意志薄弱的时刻编辑掉的黑名单；而这个依赖的是你在会话开始时自己声明的目标，需要一个模型去判断相关性。而这种判断，现在已经便宜到可以跑在每一个标签页上了。

每一次 AI 功能发布的反面，而且是拿数字撑起来的。有人把 25 个热门 App Store 应用的 2590 条评论过了一遍——这些应用平均 4.71 星、合计 1780 万条评分，其中 741 条是一星——并统计了每类抱怨命中了这 25 个应用中的多少个。付费墙和加购推销：25 个里 18 个。崩溃、bug、丢失连续打卡记录或数据：15 个。计费问题和退订困难：13 个。专门针对 AI 功能的——摘要肤浅、机器人嗓音、AI 答错：11 个。弹窗和通知：11 个。他的观察才是值得据此行动的：几乎没有一条是在说核心功能做得差，人们喜欢这些应用做的事，他们生气的是这些应用对待他们的方式。而这等于一张长期有效的邀请函——同样的核心功能，价格写清楚，退订容易，永远不弄丢别人的进度，不弹窗。

一个几乎没人点出来的遗产规划缺口：遗嘱一旦进入遗嘱认证程序就成为公开的法院记录，所以银行密码、保险箱密码或助记词不可能写进去——写进去就意味着迟早任何人都能读到。要做的东西是：给每一个你信任的人写一封密封信，设定一条打开的规则——他给的默认是「你沉默九十天之后」，并且在此之前会有连续数周的警告——而且没有任何单一一方（包括运营方自己）能提前打开它。它已经在 iPhone 上跑起来了，用硬件密钥登录。他自己抛出的那个问题才是对的，而且是定位问题而不是工程问题：这东西在人们脑子里到底算「数字遗产」、算密码管理器，还是算遗产工具？因为那是三个不同的买家，而今天只有其中一个在找你。

一位 IT 经理提出了一个没有任何产品在对准的威胁模型：某个用户的云邮箱账号已经被攻陷，攻击者没有别的访问权，而且他什么都不做——他潜伏下来，只是读。没有转发规则，没有群发，没有新的收件箱规则，没有横向移动，没有任何一个邮件安全产品被调教去触发的信号。他问的是：有没有工具能扫出并检测这种情况。有意思的地方在于，信号几乎肯定是存在的——不符合该员工作息时间的阅读模式、看起来像「采集」而不是「阅读」的连续打开序列——而没人做出这个检测器，是因为这个市场里所有东西都是靠「阻止某个动作」来卖的，而这个攻击者从不采取任何动作。

一位安全工程师正准备手搓一条针对 Teams 滥用模式的检测规则，但先问了一句：这东西是不是哪儿已经有了？他要检测的是：一个聊天参与者的显示名和某位真实员工的名字一致，而这个账号背后的主体却挂在一个外部租户域上——也就是一个访客账号借用了员工的显示名。他已经写出了能跑的查询语句，并且明说：这感觉是个足够常见的模式，大厂应该早就覆盖了——而没人能告诉他确实有。可推广的版本比单一平台大得多：显示名是人类会去读、而没有任何人会去校验的那个字段，横跨每一个支持访客的协作工具。

一条把整个问题用两行讲完的创业请求：你有一个已经规模化的硬件应用，需要在一周内拿到十万个零件。谁在做这件事？它之所以是一个真实缺口而不是一句物流抱怨，是因为现有的两个答案在同一个方向上失效——代工的定价和排期是围绕以周或月计的交期设计的，而分销商的库存定价是按个位数和十位数的量来的。「七天十万件」这条赛道没有商业模式，这也是为什么硬件公司处理这件事的方式，是让某个人把他认识的所有人挨个打一遍电话。

这是一个反复换着衣服出现的需求的「通勤电台版」。本地一家体育谈话电台关了，节目搬到了直播流和播客应用上——但直播在视频平台上，意味着开车时得一边翻一边找；而播客应用适合事后补听，对「听现场」毫无用处。他想要的是把所有正在直播的节目放在一个地方，配一个适合开车用的界面；收尾时他说，如果没有的话，也许该有人做一个。可推广的部分跟体育无关：当一个分发渠道死掉时，内容活了下来，但那个「调谐器」没有；而没人去重建调谐器，因为它没有主人。

生态产品雷达

上周发布的那个带类型的判断模型，是唯一一个被提到三次及以上的产品，而这三次全都是缺口而不是称赞：有人问谁在基于它做给 agent 用的决策引擎；有人要一个开源版本当备胎，因为一个还要排队申请的闭源 API 如今已经成了很多人配置里的承重结构；还有人要一个屏蔽器，把关于它的那些套壳推文从信息流里滤掉。一个品类、一份对冲、以及一个降噪器——全都发生在它公开可用后的四天之内。

编码 harness 通篇出现，但它们是环境而不是主题：把 skills 和规则从一个共享仓库同步到好几个 harness，以及随之而来的冲突策略问题——当其中两个在不同分支上重写同一份指令文件时该怎么办。

除此之外没有任何东西达到三次提及。值得记一笔的是，这些关键词反而被什么占领了：一个空间数据项目和一个健康追踪项目，两者加起来占掉了本窗口「the missing layer is」和「the hard part is」绝大部分的命中，而且几乎全是回复农场的文本，后面不挂任何真实需求。
