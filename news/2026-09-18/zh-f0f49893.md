# 灵感雷达: 2026-09-19

> 来源 / Source: https://clauday.com/zh/article/f0f49893-5b09-4b52-b4bc-c963fefd5905

这个窗口里有一层被五个看起来彼此并不知道对方存在的人分别描述了五遍，而它正是已经连续出现十三个窗口的那一层：没有人能证明一个 agent 在动手那一刻究竟被允许做什么。最锋利的那个版本把两件事分开了——「发生了什么的 trace」和「每个动作发生时权限处于什么状态的日志」，而这正是取证和审计之间的差别。与之并行的是，四个人用四套完全不同的词汇描述了验证缺口，却没有一个人落到一个共同的名字上。离开 agent 这块，信号最强的发现再一次是实体的：一个大批量拆水表的水暖工，已经自己推理到了那个本该存在的工具的确切形状；一个木工的铣刀烧痕，恰好长在挡住修复工具的那个几何位置上；以及一位航空投资人指出，现在制约私人飞行增长的是机库容量而不是飞机。

给会动钱的 AI agent 做保险。当 agent 开始自主下单、付款、转账，总得有人为出错的那一刻承保，而现在的 agent 已经会买错东西、把钱打到不该去的地方、或者误解用户到底要什么。定价模型本身就是产品：按每个 agent 的交易限额、历史出错率、可执行的动作范围、审批与权限控制、风控与安全基础设施、以及它能碰到多少钱来承保，再据此给保额定价。任何能自主花钱的 agent，最终都需要底下垫一层保险，而承保方最后会握有唯一一份跨厂商的「agent 到底多久出一次错」的数据集。

有人拿一个真实的多 PR 任务，认真给 Cursor Projects 试了三天，回来时带着一份「agent 控制平面绝对不能做什么」的完整规格。它把重要的细节抽象掉了，代码变得很难看清，关联产物——计划、PR、diff——完全没有交代，没有 worktree 管理，也看不到子 agent 的状态。最要命的是心理层面：因为编排者几乎不说话，它听起来比实际更聪明，于是不停发消息会上瘾，因为结果看上去「差不多行」，直到你花一整天手工清理这堆稀烂的东西。任何要做多 agent 协调器的人，现在手上有了一份由认真用过的人写出来的检查清单。这已经是同一个产品形状——一个地方看见并指挥所有 agent——从不同方向浮现出来的第四个以上的窗口了。

所有人都在做「能干更多事」的 agent，而他花了两周做一个「少干事」的。他给了它一份有真实后果的活，第三天它找到一步看起来完美、所有信号都说「上」的操作，然后它拒绝了，摆出自己为什么不确定，停在那儿等他。让 agent 动起来现在很容易，让它停下来几乎没人在做。他把这件事提炼成四条规则，现在每个 agent 都带着：动手之前先亮出推理过程；有一条它永远不能越过的硬线，哪怕有九成把握；任何不可撤销的动作必须先拿到人的同意；「我不确定」是一个完整的答案。大多数 agent 失败不是因为笨，是因为没有任何东西告诉过它什么时候该冻住。产品就是那个刹车，而现在这个刹车是一段提示词，不是一个你能买到的组件。

这个窗口里对 agent 治理缺口最锋利的一次表述，而且它把所有人混为一谈的两件事分开了。缺的那一层是可重放性：把每一次工具调用和动作，与当时的状态快照加权限快照关联起来，再记录下 agent 为什么被允许继续。一份最终的 trace 可以显示发生了什么，却让授权决策本身无法被审计——而这正是目前大多数可观测性产品交付的那种失败形态。你要的不是一份动作日志，而是一份「每个动作发生时权限处于什么状态」的日志，这样你能重放的是决策而不只是结果。这已经是 agent 授权与审计作为一个未被填上的层，连续出现的第十三个窗口，而这是迄今最干净的表述。

支付和隐私计算都是有用的原语，但缺的那一层是授权：是哪个人类允许这个 agent 花钱的、限额是多少、以及服务方能不能在不多知道任何东西的前提下验证这一点。最后那半句是大多数方案会丢掉的。目前摆在桌面上的所有设计，要么让商户为了信任 agent 而必须知道用户是谁，要么让用户去信任商户不会过度采集。一个「能证明委托授权但不泄露委托人」的验证原语，才是真正没被解决的那块，而它跟十年前支付领域解决过的身份问题，形状是一样的。

同一周里一个互补的说法：缺的那一层是委托授权，不只是身份。消费上限、限定范围的数据访问、以及一条人可以回滚的路径。身份回答的是「谁在动作」，委托授权回答的是「它被允许做什么、以及怎么撤销」，而整个行业一直在交付前者却把它叫作后者。他追问的那句才是产品问题：你会先把哪一样暴露给 agent——域名归属证明，还是交易策略。

Hermes 强得不像话，但难的地方是为具体任务把它配好。他想要的是这么一层：你给一个目标，它替你把整套东西设计出来——目标、子目标、约束、记忆、子 agent、辅助模型——组装成一套可以直接执行的 agent 系统。今天市面上每一个 harness 都默认你在开始之前就已经知道解法的形状，这意味着受益最多的恰恰是最不需要这个工具的人。一个「从意图编译到 agent 拓扑」的东西是个真产品，而且它站在所有正在比拼运行时功能的编排框架的上游。

显式的循环是对的抽象，而难的是状态：保住工具输出、给重试设上限、让终止条件变得可观测，这样「一直跑到完成为止」才不会悄悄变成一条看不见底的成本螺旋。最后那半句点名了一个没人在卖的产品。所有人都在出循环框架，没有人出那块仪表盘——让一个长时间运行的循环，在它还在跑的时候，就能让人看清它的停止条件。这个产品的客户已经存在，他们现在的做法是事后去读账单。

给 agent 做记忆一直被当成存储问题，其实它是一套保留策略。难的不是把上一份轨迹存下来，是判断哪些成功的步骤该被提炼成一个流程、哪些只是会话垃圾、该过期。否则记忆只会变成第二个陈旧的上下文窗口，而这正是目前大多数记忆工具的失败形态。没被做出来的是晋升规则和过期规则，而它们大概应该住在工作流定义里而不是记忆库里，因为只有工作流知道什么才算一个耐用的步骤。

框架很便宜，难的是证明 agent 没有在糊弄检查。他开的方子具体到可以照着做：在工具参数和状态上放确定性的 oracle，效果好过只用 LLM 当裁判。而他问的那个问题，每支团队都该能当场答上来：你的发布闸门挂的是包含提示词注入的轨迹评测，还是只挂了走通路径的数据集。验证工具仍然是这套栈里最大的窟窿，原因在于一个跟生成器共享偏见的验证器，产出的是自信的一致意见而不是真相。

省下的三万美元是容易的部分，难的是证明 agent 抓住了那些异常而不是把它们藏起来了。走通路径上零错误，不等于运营风险为零。现在流传的每一个 agent ROI 数字，衡量的都是「成功完成的那部分工作」的吞吐量，没有一个在衡量「本该被升级上报的那部分工作」后来怎么样了。给 agent 部署做异常覆盖率审计是一个产品，而它会被卖出去的那一刻，是有人第一次让 CFO 意识到：省钱的数字和风险的数字，是从同一批运行里算出来的。

代码仓库其实已经记住了几乎所有东西，除了「为什么」。代码、文档、测试、配置和 Git 本身就已经是项目记忆了；缺的那一层是理据——被否决的方案、约束条件、以及决策过程。这是这批数据里最干净的一个缺口，因为这个东西今天以任何形式都不存在。提交信息记录的是改了什么，PR 描述记录的是提议了什么，而没有任何地方记录「考虑过然后被扔掉的是什么」——而这恰恰是编码 agent 最需要、却最缺的那份上下文。

这批数据里对 agent 商业分析得最清楚的一条，而且它点出了所有人都会漏掉的那一方。商户应该拥有服务关系：卖什么、履约、售后、退款、以及识别并回馈回头客的能力。agent 拥有用户关系：意图、偏好、被委托的权限、以及对「什么可以被共享」的控制权。但中间通常还站着第三方——那个托管、聚合、路由、或者把接口暴露给 agent 的平台——它拥有发现入口、面向 agent 的交互体验、以及大部分交易上下文，却并不拥有底层服务。所以这层关系没法靠「谁拥有接口」或者「谁处理支付」来裁定。缺的那一层是三方之间可携带、经同意的身份与归因；没有它，中间方就会默认变成客户数据的孤岛，而商户会被压缩成匿名的履约端点。

部署 AI 不是难的部分。难的是把强大的算力实时接到本地的机构知识上，同时不摧毁这家机构的主权。这一句话把整个企业级 AI 的问题压缩完了，而后半句解释了为什么大多数部署卡住：那个能让模型真正有用的集成，恰恰就是这家机构在法律上或政治上没法接受的集成。谁能做出一套模式，既交付前半句、又能被证明地保住后半句，谁就拿下了企业这个品类，而现在大家普遍认为这个位置属于某一家公司。

生态产品雷达

agent 授权、审计与委托权限这一层，在这个窗口里从五个互不相干的方向同时出现，现在是这个栏目有记录以来被描述得最多的那块空白：带权限快照的可重放性、带消费上限和回滚路径的委托授权、不泄露委托人的可验证授权、带撤销机制的结算设计、以及政策尺度上的共享事件报告。连续第十三个窗口。

验证是第二个集群，四个人用四套不同的措辞描述了同一件事：证明 agent 没有糊弄检查、证明它抓住了异常而不是藏起来、让终止条件可观测、以及在整条循环上而不是逐个组件地评估轨迹质量。

记忆与理据构成第三个集群：代码仓库记得改了什么，却不记得什么被否决了；组织记忆需要的是结果而不只是结构；agent 记忆需要的是一套晋升和过期策略，而不是更大的存储。
